## What changed on 2026-11-03

The first version ran every tool that needs Core as an Engine job, with Session-scoped packages on
Engine. That needed jobs tagged by Session, packages as job inputs, closing a Session, export formats
on jobs, and six Core changes, and it changed Engine's v1 design. It is replaced by Vasilis's brief:
`dtcc-agent`'s tool server, minus its simulation tools, moves into `apps/engine` and runs as a third
container from the Engine image, as it works today. Engine itself does not change. The decisions
withdrawn are listed at the end.

## Withdrawn on 2026-11-03

- Every tool that needs Core as an Engine job, with results as Session-scoped packages (old D4, D8).
- `/mcp` as a route in the Engine API process (old D9).
- A shared download cache volume per worker host (old D10); the tool server keeps its own (D10).
- Export artifacts inside job packages, and a `format` for export jobs (old D12).
- Engine jobs tagged by Session, packages as job inputs, closing a Session on Engine, and granting a Run to a Session (old D15, D16, D31).
- No server-side renders (old D28): `render_object` is kept.
- Releasing first with only the tools that need no Core change (old D30): no tool waits for Core.
- Six Core proposals (builders over a package, crop, inspection, comparison, spatial queries, several results).

Why: they changed Engine's v1 design, made the agent wait for Core, and were slower
(`dtcc-agent` ADR-0011: answers 30–38% slower when downloads ran as Engine jobs).

## Facts checked

- Engine retention: 30 days by default (`apps/engine/dtcc_engine/jobs.py:36`); the deployment sets 90 (dtcc-infra `deploy/engine/compose.yaml:26`).
- 2026-11-02, Bedrock in `eu-north-1` with the dev key: the Messages endpoint (`bedrock-mantle`) does not answer Sonnet 5.5; InvokeModel answers `eu.anthropic.claude-sonnet-5-5` with prompt caching.
- 2026-11-03, stateless MCP (D8): `dtcc-agent`'s server (`11f20bb`, MCP Python SDK 2.3.0) with the MCP TypeScript SDK 1.32.2 client, through nginx with default settings. Connecting, listing the 22 tools and calling them works; restarting the server between calls needs no reconnect; a wrong token gets 401. A 75 s call succeeds with SSE responses, because the server sends a ping every 15 s; with JSON responses nginx answers 504 at its 60 s read timeout. Behind a proxy the SDK refuses the proxied `Host` header unless `allowed_hosts` names it.
- 2026-11-03, load by job id (D9, D10): `dtcc-agent` `q03`'s chain without the model (point cloud, terrain raster, surface mesh, slope and aspect, render, glTF export), three 600 m × 600 m areas (0.75–1.9 M points), arms in the order A, B, B, A, against an unchanged local Engine (dtcc-engine 0.1.0, Core 0.9.8dev, one worker). Median chain: in process, fresh download 17.0 s; download as an Engine job then loaded 13.5 s; in process from the disk cache 0.6 s. The steps after the download take the same time either way. Fetching and loading a finished 8–9 MB package took 0.1–0.4 s. Polling (1 s, doubling to 5 s) added up to 5 s per job. A laptop under amd64 emulation, 3–6 runs per arm.

## Upcoming, not designed yet

- Object storage shared by Engine and Twin (operator, 2026-11-02). It would change how the tool
  server fetches packages (D9) and where artifacts are kept (D12). To learn from Vasilis: owner and
  timeline.
- Outside agents (for example Claude Desktop) using the tools over MCP: deferred. They would go
  through the backend, with each user's own sign-in and limits, never straight to the tool server.
