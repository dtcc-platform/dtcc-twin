# DTCC Engine: what Atlas gets from it

Draft. Our reading of what DTCC Engine will provide, and the approach we plan to propose to the engine team. Nothing here is agreed with them yet.

Sources: the engine spec [apps/engine/DESIGN.md](../apps/engine/DESIGN.md) (dated 2026-09-06), and the `develop` branches of dtcc-core (`9b4e9b9`) and dtcc-sim (`2422bba`) in `.temp/`. The engine is a thin layer over Core and Sim, so most of its payloads are Core's existing structures passed through.

## Where it sits

```
Atlas (browser) ──HTTP──▶ backend ──HTTP──▶ DTCC Engine ──▶ Core / Sim
```

Atlas never calls the engine directly:

- The engine authenticates with one shared token and has no per-consumer permissions, so the token must stay on the server.
- The engine keeps results for 30 days and is explicitly not a Package Catalog. Durable storage of packages, workspaces and publications is the backend's job ([spec, Downstream responsibilities](../apps/engine/DESIGN.md#downstream-responsibilities)).
- The engine only supports polling. The backend can poll it and give Atlas whatever suits the UI.

## Operations

From the spec's [consumer API contract](../apps/engine/DESIGN.md#consumer-api-contract). Route names aren't decided yet.

| Operation              | Input                                                          | Output                                                              |
| ---------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------- |
| List/describe Datasets | optional Dataset name                                          | Dataset descriptors (below) plus availability per compute target    |
| List compute targets   | none                                                           | target ids, versions, capabilities, availability                    |
| Submit a job           | Dataset name, parameters (including `bounds`), optional target | job id; returns immediately                                         |
| Job status             | job id                                                         | state, progress when measured, error, whether a result is available |
| Download a result      | completed job id                                               | a validated `.dtccpkg` archive                                      |
| Request cancellation   | job id                                                         | requested / already resolved / unsupported; queued jobs only in v1  |

Not in engine v1: uploads and imports, streaming status (SSE or webhooks), per-user permissions, retries, and cancelling running jobs.

## Dataset descriptor

The engine passes through Core's `DatasetDescriptor.describe()` (`dtcc_core/datasets/dataset.py`). Sim's existing service returns the same fields.

| Field                          | Meaning                                                                                                            |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `name`, `title`, `description` | identity and display text                                                                                          |
| `data_category`                | `raw`, `derived`, `synthetic` or `simulation`; a natural grouping for the catalogue                                |
| `result_kind`                  | semantic result type, e.g. `building_collection`, `mesh`, `road_network`, `sensor_collection`; drives presentation |
| `python_return_type`           | the DTCC Model class, e.g. `dtcc_core.model.BuildingCollection`                                                    |
| `args_schema`                  | JSON Schema generated by Pydantic from the Dataset's arguments; drives the parameter form                          |
| `supported_formats`, `formats` | optional supplemental artifact formats, with media type and kind                                                   |
| `timeout_hint`                 | expected duration in seconds, when known                                                                           |

Every Dataset's arguments include:

- `bounds`: `[minx, miny, maxx, maxy]`, or 6 values with z.
- `strict_live`: fail instead of degrading when a live source is unreachable.
- Usually an optional `format`.

**CRS:** the bounds CRS is not a descriptor field. In practice it is EPSG:3006 (SWEREF99 TM, metres); Core states it in field descriptions and in `presentation.view_hints.default_crs`.

Datasets on `develop` today:

- **Core:** `city`, `buildings`, `building_footprints`, `city_footprints`, `terrain_surface_mesh`, `city_surface_mesh`, `city_flat_mesh`, `city_volume_mesh`, `point_cloud`, `roads`, `space_syntax`, `trees`, `deso`, `weather`, `air_quality`, `hydrology`, `ocean`, `transit_vehicles`, `smoke`, `calibration_grid`.
- **Sim:** `urban_heat_simulation`, `urban_wind_simulation`, `air_quality_field`, `traffic_simulation`.

## Job status

The spec requires these states: queued, running, completed, failed, cancelled, plus unknown/expired and "status temporarily unavailable". Cancellation _requested_ is reported separately from _confirmed_.

Progress comes from Core's `ProgressTracker` (`dtcc_core/common/progress.py`): weighted phases (e.g. `buildings` has `download_pointcloud`, `download_footprints`, `build_lod1`, …), an overall percent, a message, and an ETA. The spec forbids inventing a percentage when nothing is measured, so the UI must handle "running, no progress".

## Result: the `.dtccpkg` package

Core's canonical v3 package (`dtcc_core/datasets/package.py`, `export_model_package(..., canonical=True)`) is a zip:

```text
manifest.json
artifacts/model.dtcc       canonical DTCC Model, protobuf (application/vnd.dtcc.model+protobuf)
artifacts/<supplemental>   optional: one artifact in the format the request asked for
```

The spec lists canonical protobuf in packages as missing upstream work. That was true at the revision it inspected, but Core `develop` now writes it for a subset of model types.

Recording our fixtures showed the gaps. Only model types with a canonical encoding get a v3 package; the rest fall back to the legacy v2 package, which has the same manifest sections but no `health` and no protobuf model.

| Dataset               | Canonical v3                             | GeoJSON artifact                           |
| --------------------- | ---------------------------------------- | ------------------------------------------ |
| `building_footprints` | no: `FootprintCollection` is unsupported | yes, in a v2 package                       |
| `deso`                | yes                                      | no: `DeSO` has no GeoJSON writer           |
| `trees`               | no: `TreeCollection` is unsupported      | no: `TreeCollection` has no GeoJSON writer |

`manifest.json` (`dtcc-dataset-manifest-v3`, models in `dtcc_core/datasets/schema.py`):

| Section              | What Atlas uses it for                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `identity`           | name, title, version                                                                                                           |
| `metadata`           | description, provider, source, license, CRS, LoD, coverage, `data_category`, `result_kind`                                     |
| `provenance`         | sources, processing steps, generator, time, lineage; the "where does this come from" panel                                     |
| `presentation`       | headline, summary, legend, `view_hints` (e.g. `preferred_geometry: solid_buildings`), warnings, limitations                    |
| `request`            | the exact Dataset name, parameters and bounds; enough to reproduce or re-run                                                   |
| `artifacts[]`        | per file: `path`, `role`, `format`, `media_type`, `data_kind`, `crs`, `bounds`, `size`, `sha256`, `model_type`, `derived_from` |
| `health`, `warnings` | run-time health and warnings                                                                                                   |

DESIGN requires showing provenance, warnings and limitations with every result. The manifest carries all of it, so Atlas needs no metadata of its own per Dataset.

## What a browser can display

The canonical artifact is protobuf, which the browser can't use as is. The supplemental formats Core offers today:

| Displayable how                | Datasets and formats                                                                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **2D map, after reprojection** | GeoJSON: `building_footprints`, `calibration_grid`. In a package it keeps the Dataset's CRS (EPSG:3006); only the Dataset's own `format=` path defaults to WGS84. |
| 3D, with a loader              | OBJ/STL: `buildings`, `terrain_surface_mesh`, `city_surface_mesh`, `city_flat_mesh`. CityJSON: `city`. LAS/LAZ/COPC: `point_cloud`.                               |
| Not without decoding protobuf  | `roads`, `space_syntax`, `weather`, `air_quality`, `hydrology`, `ocean`, `transit_vehicles`, `deso`, `trees`                                                      |
| Analysis formats               | VTU/XDMF (volume meshes and Sim results), TIF rasters                                                                                                             |

A package holds at most one supplemental artifact, chosen by the request's `format`.

## Approach we plan to propose

1. **Contract in zod.** We model the operations, descriptor, job status and manifest above as schemas in `packages/contracts`, and send the engine team the resulting JSON shapes as a concrete proposal instead of open questions.
2. **Browser-ready derivatives from Core.**
   - For 2D, ask for a WGS84 GeoJSON derivative for every `result_kind` that has a 2D reading (roads, sensor stations, space syntax, footprints).
   - For 3D later, ask for glTF.
   - This follows DESIGN: derived render formats are allowed as long as they stay traceable to the canonical model.
   - Fallback: decode `model.dtcc` in TypeScript, generated from `dtcc_core/schemas/dtcc.proto`.
3. **Explicit bounds CRS in the descriptor,** instead of inferring it from field descriptions.
4. **More than one supplemental artifact per package,** or a way to add a derivative to an existing result. Otherwise Atlas has to choose between a download format and a display format, or run the Dataset twice, which the spec forbids.

## How we build ahead of the engine

- The backend talks to the engine through an `EngineClient` interface. For now it is a fake; the HTTP implementation arrives when the engine exists, and nothing else changes.
- **Fixtures are real Core output, not hand-written:** `describe()` for every Dataset, and `.dtccpkg` packages for one small area, generated by running Core from `.temp/dtcc-core`.
- **The fake follows the real lifecycle:** queued → running with phased progress → completed or failed, with delays. That way polling, progress and failure handling are exercised from the start.

## Open questions (ours)

- Does Atlas unpack packages in the browser, or does the backend extract the artifacts and serve them? The backend is the likely answer: it has to store packages anyway.
- Which Datasets make the "base twin" for **Build Twin**? DESIGN leaves the recipe to product requirements.
- Do we keep EPSG:3006 bounds end to end and reproject only for display? Core's descriptors assume it, and the map needs WGS84.
